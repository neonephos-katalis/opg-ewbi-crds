# OPG EWBI Custom Resource Definitions (opg-ewbi-crds)

This repository serves as the centralized multi-component repository for Kubernetes Custom Resource Definitions (CRDs) across the GSMA Operator Platform Group (OPG) East/WestBound Interface (EWBI) federation ecosystem.

The repository is structured to host CRDs from multiple components of the EWBI platform. Currently, it contains the CRDs for `opg-ewbi-operator`, and is designed to accommodate additional CRDs from future components as the platform expands.

Downstream projects can import Go API types as standalone modules without depending on operator controllers or heavy runtime dependencies.

## Testing and Installing CRDs

### 1. Prerequisites
- A Kubernetes cluster version 1.24 or later (such as Kind or Minikube).
- `kubectl` configured with cluster administrator credentials.

To start a clean local testing cluster with Kind:
```bash
kind create cluster --name ewbi-test
kubectl config use-context kind-ewbi-test
```

### 2. Installation Options

#### Option A: Install All Platform CRDs (All Components)
To install CRDs for every registered component:
```bash
kubectl apply -f install.yaml
# or:
make install
```

#### Option B: Install CRDs by Component
To install only the operator component CRDs:
```bash
kubectl apply -f crds/operator/install.yaml
# or:
make install-operator
```

Using Kustomize:
```bash
kubectl apply -k crds/operator/
```

### 3. Verifying CRD Registration

Verify that the CRDs are established in the Kubernetes API:
```bash
kubectl get crd | grep "opg.ewbi.katalis.com"
```

Expected output:
```
applicationdeployments.opg.ewbi.katalis.com     <date>
applicationonboardings.opg.ewbi.katalis.com     <date>
artefacts.opg.ewbi.katalis.com                  <date>
availabilityzones.opg.ewbi.katalis.com          <date>
consumptionmonitorings.opg.ewbi.katalis.com     <date>
federations.opg.ewbi.katalis.com                <date>
images.opg.ewbi.katalis.com                     <date>
```

### 4. Testing Resource Instantiation

Create a test namespace:
```bash
kubectl create namespace test-federation
```

Apply a test `Federation` custom resource:
```bash
cat <<EOF | kubectl apply -f -
apiVersion: opg.ewbi.katalis.com/v1beta1
kind: Federation
metadata:
  name: test-federation-host
  namespace: test-federation
spec:
  federationData:
    relationType: HOST
    technologyType: REST
    origOPFederationId: op-test-01
    origOPCountryCode: IT
    initialDate: "2026-01-01T10:00:00Z"
    restOptions:
      partnerStatusLink: "http://partner.example.com/callback"
EOF
```

Verify that the resource is accepted and stored:
```bash
kubectl -n test-federation get federations
kubectl -n test-federation get federation test-federation-host -o yaml
```

Clean up the test resources:
```bash
kubectl -n test-federation delete federation test-federation-host
kubectl delete namespace test-federation
```

### 5. Uninstalling CRDs

To remove all CRDs across all components:
```bash
kubectl delete -f install.yaml
# or:
make uninstall
```

To remove only the operator CRDs:
```bash
kubectl delete -f crds/operator/install.yaml
# or:
make uninstall-operator
```

## Adding CRDs for a New Component

When a new component requires Custom Resource Definitions:

### Step 1: Create the Component Go API Directory
Under `apis/`, create a new component folder and version directory:
```bash
mkdir -p apis/<new-component>/<version>
```
Example: `apis/telemetry/v1alpha1/`.

### Step 2: Implement the Types
Place your Go struct definitions inside `apis/<new-component>/<version>/`:
- Define the `+kubebuilder` markers for validation, status subresource, and printer columns.
- Include `groupversion_info.go` defining the `schema.GroupVersion` and `SchemeBuilder`.

### Step 3: Run Multi-Component Generation
Execute the Makefile targets from the root of the repository:
```bash
make generate    # Generates zz_generated.deepcopy.go across all components
make manifests   # Generates YAML manifests into crds/<new-component>/bases/ and updates install.yaml
```

The Makefile automatically discovers any new subdirectories in `apis/*`, runs `controller-gen`, creates `crds/<new-component>/install.yaml`, and aggregates all manifests into the root `install.yaml`.

### Step 4: Validate
Format and vet the Go code:
```bash
make fmt
make vet
```

## Importing the Go Module

Downstream components can import specific API packages:

```bash
go get github.com/neonephos-katalis/opg-ewbi-crds@latest
```

Example usage in Go:
```go
package main

import (
    "k8s.io/apimachinery/pkg/runtime"
    utilruntime "k8s.io/apimachinery/pkg/util/runtime"
    
    operatorv1beta1 "github.com/neonephos-katalis/opg-ewbi-crds/apis/operator/v1beta1"
)

func main() {
    scheme := runtime.NewScheme()
    utilruntime.Must(operatorv1beta1.AddToScheme(scheme))
}
```

## Continuous Integration and Automated Testing

This repository includes a GitHub Actions test workflow (`.github/workflows/test-crds.yml`) triggered on every push and pull request against `main`:

1. Code Quality: Runs `go fmt` and `go vet`.
2. Generator Consistency: Executes `make generate && make manifests` and checks for uncommitted changes to ensure manifests stay in sync with Go structs.
3. Kind Cluster Validation: Creates an ephemeral Kind cluster, applies `install.yaml`, and verifies that all CRDs reach the `Established` state.
4. Custom Resource Schema Testing: Creates the `guest` namespace, applies all sample CRs from `examples/operator/rest/` and `examples/operator/k8s/`, and verifies that the Kubernetes API server validates and accepts every resource without schema errors.

## Automated Upstream Synchronization

This repository includes a GitHub Actions workflow (`.github/workflows/sync-upstream.yml`) configured to synchronize operator CRD definitions from the `main` branch of the upstream repository [neonephos-katalis/opg-ewbi-operator](https://github.com/neonephos-katalis/opg-ewbi-operator).

- Upstream Source: https://github.com/neonephos-katalis/opg-ewbi-operator
- Triggers:
  - Scheduled execution every 6 hours.
  - Manual trigger via `workflow_dispatch`.
  - Repository webhook dispatch via `repository_dispatch` (event types: `opg-operator-updated`, `upstream-sync`).
- Behavior:
  - Checks out `https://github.com/neonephos-katalis/opg-ewbi-operator` (branch `main`).
  - Synchronizes Go types into `apis/operator/v1beta1/` and YAML manifests into `crds/operator/bases/`.
  - Regenerates `crds/operator/install.yaml` and the root `install.yaml`.
  - If changes are detected, it updates the dedicated branch (`automation/sync-operator-crds`), attempts PR creation, and posts a GitHub Actions summary containing a 1-click comparison link to open the Pull Request.
